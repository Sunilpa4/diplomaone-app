Q.1 (b) Which model is used for online shopping system. Justify it4 marks

Question as printed: Q.1 (b) Which model is used for online shopping system. Justify it

A suitable choice is an Agile iterative-incremental model. Online-shopping requirements and user expectations change, and the system can be divided into useful increments—for example, catalogue/search, cart, checkout/payment and order tracking. Each short iteration delivers tested functionality, obtains customer feedback and adjusts priorities before later increments. This reduces the risk of building the wrong user experience and allows early releases.

Because checkout and payment are security-sensitive, each increment should include security, integration and regression testing; payment authorization must be verified before confirming an order. If the project had unusually high technical or regulatory risk, a risk-driven Spiral process could also be justified, but iterative Agile delivery is a practical general choice.

Q.1 (c) Write a short note on prototype model7 marks

Question as printed: Q.1 (c) Write a short note on prototype model

The prototyping model builds an early, simplified version of a system so users can explore it and clarify requirements. A typical cycle is: communicate with users and define initial objectives; make a quick design; build the prototype; obtain user evaluation; refine requirements and prototype; repeat until requirements are understood; then engineer, test and deliver the production system.

It is useful when requirements or user interfaces are unclear, as in a new online service. It encourages early feedback and exposes omissions. Risks include users mistaking a prototype for production software, developers carrying temporary shortcuts into the final product, and scope growth. A throwaway prototype is discarded after learning; an evolutionary prototype is refined into the delivered system. The production design still needs proper architecture, security and testing.

Q.1 (c) OR Explain Classical Waterfall Model with diagram7 marks

Question as printed: Q.1 (c) OR Explain Classical Waterfall Model with diagram

The classical Waterfall model is a plan-driven process in which development proceeds through ordered phases, with each phase producing documented outputs for the next:

  1. Requirements analysis and specification.
  2. System/software design.
  3. Implementation and unit testing.
  4. Integration and system testing.
  5. Deployment/operation.
  6. Maintenance and correction after delivery.

Reviews and approval gates help control transitions. Advantages: clear milestones, documentation and progress tracking; works reasonably well when requirements and technology are stable. Limitations: working software arrives late, changes can be expensive, and misunderstandings may not be discovered until testing. Real projects often need feedback loops back to earlier phases, even if the classical diagram is linear.

Q2 · Requirements, Agile and UML

Q.2 (a) Explain any two requirement gathering techniques3 marks

Question as printed: Q.2 (a) Explain any two requirement gathering techniques

1. Interviews: a requirements analyst asks users, customers and other stakeholders structured or open-ended questions, follows up on unclear answers, and records needs, constraints and priorities. Interviews provide depth and are useful for complex tasks, but can be time-consuming and affected by interviewer bias.

2. Observation: the analyst watches users perform real work in its normal setting, noting actual tasks, exceptions, hand-offs and workarounds. It reveals needs people may forget to mention, but observed behaviour may be atypical and the method takes time. Findings should be validated with stakeholders and documented as testable requirements.

Q.2 (c) Explain Sequence diagram with example7 marks

Question as printed: Q.2 (c) Explain Sequence diagram with example

A UML sequence diagram is an interaction diagram showing how actors and objects exchange messages over time to complete one scenario. Participants are shown as lifelines; time flows downward. Horizontal arrows represent messages/calls and dashed arrows commonly represent returns. Activation bars show when a participant is executing; frames such as alt can show alternatives.

Example: a customer submits an online purchase. The web app asks the order service to create a pending order; the order service checks availability and temporarily holds the stock, then requests payment authorization. If payment is approved, the hold is committed and confirmation is returned; if it fails, the hold is released and the customer can retry or cancel.

The diagram makes message order and responsibility explicit; it is useful for validating interfaces and identifying missing responses or error cases.

Q.2 (a) OR List characteristics of good SRS3 marks

Question as printed: Q.2 (a) OR List characteristics of good SRS

A good Software Requirements Specification (SRS) should be:

  • Correct: reflects actual stakeholder needs.
  • Unambiguous: each requirement has one interpretation.
  • Complete: includes required functions, constraints, interfaces and responses to relevant conditions.
  • Consistent: requirements do not contradict one another.
  • Verifiable/testable: an objective method can determine whether each requirement is met.
  • Feasible: achievable within technology, cost, schedule and legal constraints.
  • Prioritized: importance and stability are ranked.
  • Modifiable and traceable: changes can be made coherently and requirements can be linked to sources, design and tests.
Q.2 (b) OR Explain any 4 Agile principles4 marks

Question as printed: Q.2 (b) OR Explain any 4 Agile principles

Four principles from the Agile Manifesto’s twelve principles are:

  1. Satisfy the customer through early and continuous delivery of valuable software, so useful capability arrives before the whole project is complete.
  2. Welcome changing requirements, even late in development, when they improve customer value; evaluate and reprioritize changes rather than blindly following an obsolete plan.
  3. Deliver working software frequently, in short timescales, and use the running product as a primary progress measure.
  4. Business people and developers collaborate daily, enabling timely clarification and shared decisions.

Agile also emphasizes sustainable pace, technical excellence, simplicity, self-organizing teams and regular reflection. Agile does not mean “no planning” or “no documentation”; it favors planning and documentation appropriate to the work.

Q.2 (c) OR Explain Activity diagram with example7 marks

Question as printed: Q.2 (c) OR Explain Activity diagram with example

A UML activity diagram models a workflow or business process. It uses an initial node, action nodes, control-flow arrows, decision/merge diamonds with guards, optional fork/join bars for parallel work, and a final node.

Example: an online-shopping checkout begins with cart review. The customer chooses online payment or cash on delivery. For online payment, the system requests gateway authorization; if approved it creates the order, otherwise it displays failure and allows retry/cancellation. For cash on delivery it creates the order directly. Both successful branches send confirmation and finish.

The diagram clarifies alternative and parallel flows; labels on decision arrows should be guards such as [approved] and [declined], and every action should have an unambiguous next step.

Question as printed: Q.3 (a) Explain function point with example

Function Point (FP) analysis estimates software size from functionality delivered to users, independent of a particular programming language. It counts five function types: External Inputs (EI), External Outputs (EO), External Inquiries (EQ), Internal Logical Files (ILF) and External Interface Files (EIF). Each item is rated simple, average or complex and multiplied by its standard weight.

With a total Degree of Influence (sum of Fi) of 30 across the 14 general system characteristics, VAF = 0.65 + 0.01×30 = 0.95; adjusted FP = 27×0.95 = 25.65 FP. Q.3 (c) Explain cohesion in detail7 marks

Question as printed: Q.3 (c) Explain cohesion in detail

Cohesion measures how strongly the responsibilities within one module belong together. High cohesion is desirable: a module with one focused purpose is easier to understand, test, reuse and change. The traditional categories from weakest to strongest are:

Type (low → high)Meaning / example
CoincidentalUnrelated tasks are placed in one module, such as a miscellaneous utility that prints a report, calculates tax and resets a database.
LogicalSimilar kinds of operations are grouped and selected by a control flag, such as one input module handling keyboard, file and network input.
TemporalOperations are grouped because they occur at the same time, such as startup initialization of unrelated subsystems.
ProceduralElements are grouped because they follow a particular sequence, but may operate on unrelated data.
CommunicationalOperations are grouped because they use the same data set, such as reading and formatting the same customer record.
SequentialThe output of one part is the input to the next, such as tokenize → parse → validate.
FunctionalEvery element contributes to one well-defined function, such as calculate_invoice_total.

Design should aim for functional (or otherwise strong) cohesion. Splitting unrelated responsibilities reduces the ripple effect of change and makes module-level testing clearer.

Q.3 (a) OR Explain LOC with example3 marks

Question as printed: Q.3 (a) OR Explain LOC with example

LOC (Lines of Code) is a size metric that counts source-code lines in a software product. The counting convention must be stated: physical or logical lines, whether comments/blank lines are counted, and whether generated or reused code is included. KLOC means thousands of LOC.

Example: if a project has 1,200, 800 and 500 counted source lines in three modules, total size = 1,200+800+500 = 2,500 LOC = 2.5 KLOC. If the team used 50 person-months, productivity by this metric would be 2,500/50 = 50 LOC per person-month.

LOC is easy to measure after coding, but is language-dependent, difficult to estimate early, and may reward verbose code rather than delivered functionality.

Q.3 (c) OR Explain coupling with example in detail7 marks

Question as printed: Q.3 (c) OR Explain coupling with example in detail

Coupling is the degree of dependency between modules. Low coupling is preferred because a change in one module then has less impact on others. Traditional coupling types, roughly from strongest/worst to loosest/best, are:

TypeExplanation / example
ContentOne module directly accesses or changes another module’s internal code/data.
CommonSeveral modules share global data; one change can unexpectedly affect all users.
ExternalModules depend on an externally imposed format, device interface or protocol.
ControlOne module passes flags that dictate another module’s internal logic.
Stamp (data-structured)A whole record/structure is passed even though the receiver uses only a small part.
DataModules communicate only the necessary data items as parameters.
MessageObjects/components communicate through narrow messages or interfaces without sharing internals.

Example: instead of letting a checkout module modify an inventory module’s global stock array (common/content coupling), it should call a defined reserveItem(itemId, quantity) interface (lower data/message coupling). Aim for high cohesion within modules and low coupling between them.

Q.4 (a) Give Difference between verification and validation3 marks

Question as printed: Q.4 (a) Give Difference between verification and validation

Verification asks, “Are we building the product right?” It checks work products against specifications through reviews, inspections, static analysis and other activities; it does not necessarily execute the software. Validation asks, “Are we building the right product?” It evaluates the implemented software with users or representative tests to confirm it meets intended needs.

Q.4 (c) Explain responsibilities of software project manager7 marks

Question as printed: Q.4 (c) Explain responsibilities of software project manager

A software project manager (PM) plans and coordinates work so the team can deliver agreed scope, quality and value within constraints. Key responsibilities include:

  • Clarify objectives, scope, assumptions, deliverables and success criteria with stakeholders.
  • Estimate size, effort, cost, staffing and schedule; prepare a work breakdown structure and dependencies.
  • Organize the team, assign responsibilities, support communication and resolve impediments.
  • Track progress against the plan, manage changes and report status to customers and sponsors.
  • Identify, assess, prioritize, mitigate and monitor project risks; maintain a risk register and contingency plans.
  • Plan quality activities, reviews, testing, configuration/change management and acceptance criteria.
  • Manage resources, procurement, team coordination and stakeholder expectations; ensure project documentation and handover.

The PM facilitates delivery and decisions; the role does not replace technical ownership or the team’s responsibility for quality.

Q.4 (a) OR Explain code walk through techniques3 marks

Question as printed: Q.4 (a) OR Explain code walk through techniques

A code walkthrough is a peer review in which the author leads reviewers through source code, design or another work product, often using a checklist and representative scenarios. Participants ask questions, trace logic and record defects or improvement points. The author then corrects the agreed issues.

It is a static verification technique: the code need not be executed. A walkthrough is generally less formal than a formal inspection—roles and preparation may be lighter, and the author typically explains the work. It finds defects early and shares knowledge, but is not a substitute for testing.

Q.4 (c) Write a short note on: COCOMO Model7 marks

Question as printed: Q.4 (c) Write a short note on: COCOMO Model

COCOMO (Constructive Cost Model), proposed by Barry Boehm, estimates software effort and schedule from project size in KLOC. Basic COCOMO classifies a project as organic (small/familiar), semi-detached (mixed experience/constraints) or embedded (tight hardware, operational or regulatory constraints).

ModeEffort E (person-months)Development time D (months)
Organic2.4 × KLOC^1.052.5 × E^0.38
Semi-detached3.0 × KLOC^1.122.5 × E^0.35
Embedded3.6 × KLOC^1.202.5 × E^0.32

Average team size is approximately E/D. For example, an organic 10-KLOC project gives E = 2.4×10^1.05 ≈ 27 person-months, D = 2.5×27^0.38 ≈ 8.7 months, and average team size ≈ 3 people.

Intermediate COCOMO multiplies basic effort by an Effort Adjustment Factor derived from cost drivers (product, hardware, personnel and project attributes). Detailed COCOMO further allocates effort across life-cycle phases. COCOMO is an estimate, not a guarantee; uncertain size, assumptions and risks should be documented and estimates revised as evidence improves.

Q.5 (b) Explain risk mitigation and planning4 marks

Question as printed: Q.5 (b) Explain risk mitigation and planning

Risk planning decides in advance how the project will handle uncertain events that may affect cost, schedule, scope or quality. For each risk, record its description, probability, impact, priority/exposure, owner, trigger, mitigation, contingency and review date.

Risk mitigation reduces the probability or impact before the risk occurs. Common strategies are:

  • Avoid: change scope/approach to remove the exposure (for example, use a proven payment provider instead of building a new payment protocol).
  • Reduce: take action to lower likelihood or impact (for example, prototype an unfamiliar integration early, add backups or cross-train a critical specialist).
  • Transfer/share: allocate part of the impact to a suitable third party by contract or insurance, while retaining oversight.
  • Accept: consciously monitor a low-priority risk and prepare a contingency if it occurs.

Mitigation tasks belong in the project plan with owners and due dates. A contingency plan describes what to do if the trigger occurs; it is different from prevention.

Q.5 (c) Explain any two black box testing methods7 marks

Question as printed: Q.5 (c) Explain any two black box testing methods

Black-box testing derives test cases from requirements and externally observable behaviour without examining internal source code.

1. Equivalence Class Partitioning (ECP): divide the input domain into groups expected to behave similarly; select representative values from each valid and invalid class. For an age field accepting integers 18–60, classes include below 18 (invalid), 18–60 (valid), and above 60 (invalid). Tests such as 17, 35 and 61 represent those classes.

2. Boundary Value Analysis (BVA): test values at and immediately around class boundaries because off-by-one errors are common. For the same inclusive range, test 17, 18, 19, 59, 60, 61 (and representative interior values if needed).

ECP reduces redundant tests; BVA concentrates on edge conditions. Both should be combined with expected results, and neither guarantees internal code coverage.

Q.5 (b) OR Explain Risk monitoring and risk control4 marks

Question as printed: Q.5 (b) OR Explain Risk monitoring and risk control

Risk monitoring repeatedly checks identified risks, watches for triggers and new risks, and updates probability, impact and exposure as the project changes. The risk owner reports evidence and status at scheduled reviews; the risk register records changes.

Risk control acts on that information: execute the planned mitigation or contingency, add corrective actions, reassign an owner, escalate a high exposure, or close a risk when it is no longer relevant. The PM checks whether the response reduced exposure and whether it introduced secondary risks. Monitoring and control continue throughout the life cycle and feed the next round of identification and planning.

Q.5 (c) OR Explain any two white box testing methods7 marks

Question as printed: Q.5 (c) OR Explain any two white box testing methods

White-box testing selects tests using knowledge of internal code structure and control flow.

1. Statement coverage: measure whether each executable statement has run at least once. For if (x > 0) y = f(x); else y = g(x);, a test with x=3 executes the true-branch statement but not the else statement; it does not achieve full statement coverage.

2. Branch (decision) coverage: ensure every decision outcome is taken. For the same if/else, tests x=3 and x=−1 exercise both true and false branches, giving 100% branch coverage for that decision.

Coverage helps expose untested code, but even 100% statement or branch coverage cannot prove correctness for all inputs. Other techniques include condition coverage and basis-path testing using cyclomatic complexity.

Branch coverage is stronger than statement coverage for this example because it requires each decision outcome.
